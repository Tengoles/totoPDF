# totoPDF — Spanish localization

Status: approved for planning. Written 2026-08-13.

## 1. Problem and goals

Every user-facing string in totoPDF is a hardcoded English literal. This
design adds Spanish and, in doing so, builds the mechanism that makes any
third language a data change rather than a code change.

Goals:

- Every string a user can read in ordinary use is available in Spanish.
- A missing or misspelled message key is a compile error, not a blank button.
- The existing unit tests keep asserting real copy without mocking `chrome`.
- Nothing about the save pipeline, the annotation model or stored settings
  changes shape. This is a presentation-layer change.

## 2. Non-goals

- No in-app language picker. The language follows Chrome's UI language and
  nothing else. Adding a picker later means replacing `t()`'s body, not its
  call sites.
- No runtime language switching. `chrome.i18n` resolves once per page load,
  which is the only thing a picker would have to change.
- No localization of pdf.js's own internals. See §8.
- No translation of the store listing. That belongs to the store-readiness
  cycle, which is separate work.

## 3. Key decisions

**Chrome's native `chrome.i18n`, not a custom string table.** It is what the
Web Store expects, it costs no runtime machinery, and it localizes the
manifest — which a custom table cannot do at all.

**One Spanish catalogue, at `es`, not `es_419`.** Chrome's fallback chain is
`es_419` → `es` → `default_locale`. A catalogue shipped only at `es_419`
therefore serves English to any user whose Chrome is set to plain "Español",
which is common throughout Argentina and Uruguay. A catalogue at `es` serves
Spanish to `es`, `es_419`, `es_AR`, `es_UY` and `es_ES` alike. The copy is
Latin American tuteo regardless; the locale code only decides who receives
it, and `es` is a strict superset of `es_419`.

**Tuteo, not voseo.** It matches what Chrome itself ships in Spanish, so
totoPDF does not read as a different voice from the browser around it.

**Catalogues live in `src/i18n/`, not `public/`.** Vite warns when JavaScript
imports out of `publicDir`, and `src/core/i18n.ts` must import the English
catalogue (§5). The build copies them into place instead (§6).

**Message keys are a TypeScript union.** `chrome.i18n.getMessage` returns the
empty string for an unknown key and logs only to the console — a silently
blank control. Deriving the key type from the English catalogue makes the
whole class of error unwritable.

**Only failures a user can cause are translated.** Four invariant violations
stay English so a bug report stays greppable. Listed in §7.

## 4. Catalogue format

`src/i18n/en.json` and `src/i18n/es.json`, both in Chrome's `messages.json`
format. English is the source of truth: Spanish is validated against it, not
the other way round.

Interpolation uses Chrome's `placeholders`, never string concatenation, so a
translation can reorder its arguments:

```json
{
  "loadFailedHttp": {
    "message": "No se pudo cargar $URL$ (HTTP $STATUS$).",
    "placeholders": {
      "url": { "content": "$1" },
      "status": { "content": "$2" }
    }
  }
}
```

Chrome allows at most nine placeholders per message. Nothing here needs two.

## 5. `src/core/i18n.ts`

The whole module, roughly 25 lines:

```ts
import en from '../i18n/en.json';

export type MessageKey = keyof typeof en;

export function t(key: MessageKey, ...subs: string[]): string;
```

Two behaviours matter.

**In the extension**, `t()` delegates to `chrome.i18n.getMessage(key, subs)`.

**Outside it** — vitest's node environment, where `chrome` is undefined —
`t()` reads `en.json` directly and substitutes `$1`…`$9` itself. This is why
the catalogue is imported rather than merely copied: the twenty existing unit
specs go on asserting the real English copy with no `chrome` mock and no
change to how they are written.

The cost is that `en.json` (~4KB) is inlined into `viewer.js`. Accepted.

Callers may hold results in module-level constants. `chrome.i18n` resolves
synchronously and the locale cannot change for the lifetime of a page, so
`const ENCRYPTED_REASON = t('encryptedReason')` is sound. No call site needs
to become lazy.

## 6. Build and manifest

`vite.config.ts` already has a `closeBundle` plugin that copies pdf.js
assets. It grows a second responsibility: copy `src/i18n/<locale>.json` to
`dist/_locales/<locale>/messages.json`. It is renamed from `copyPdfjsAssets`
to `copyStaticAssets` to reflect that it is no longer only about pdf.js.

`public/manifest.json` gains `"default_locale": "en"` and replaces three
literals with message references:

| Field | Value |
|---|---|
| `name` | `__MSG_extensionName__` |
| `description` | `__MSG_extensionDescription__` |
| `action.default_title` | `__MSG_actionTitle__` |

`default_locale` is mandatory once `_locales/` exists; Chrome refuses to load
the extension without it.

### 7.1 Palette names

`PaletteEntry.name` currently does four jobs at once: it is persisted in
`chrome.storage`, serialized into pdf.js's `name=#RRGGBB` colour string,
shown in the swatch tooltip, and used as the label in pdf.js's own highlight
colour menu.

Localizing the stored value would leave a Spanish name sitting in an English
UI after a locale change, and would need a storage migration.

Instead: `name` stays the stable ASCII id it already is, and a new
`paletteDisplayName(id)` localizes at the point of display. It falls back to
the id itself for any name it does not recognise, which keeps
`normalizeSettings`' existing tolerance of hand-edited storage intact.

`paletteToHighlightColors()` serializes the *display* name, which localizes
pdf.js's built-in colour menu at no extra cost. Two constraints hold:

- The five Spanish names (Amarillo, Verde, Azul, Rosa, Naranja) are ASCII, so
  the existing `SAFE_NAME` guard `^[A-Za-z0-9 _-]+$` still passes.
- None contains `,` or `=`, which pdf.js's own parser splits on.

No storage migration. No change to `withPaletteColor` or `normalizeSettings`.

### 7.2 A constraint on the swatch strings

`palette.ts` carries a comment forbidding the word "highlight" in a swatch
title, because the e2e specs locate the Highlight button by accessible name
and Playwright matches by substring. The same constraint applies to the
Spanish copy and the word "Resaltar". It binds the English catalogue in
practice (§9 pins e2e to `en-US`), but both catalogues should honour it so
that pinning is a convenience rather than a load-bearing decision.

### 7.3 Document language

`viewer.html` hardcodes `lang="en"`, which tells a screen reader to read
Spanish with English phonetics. `document.documentElement.lang` is set from
`chrome.i18n.getUILanguage()` during startup.

## 8. What stays English

Deliberate, and each for a stated reason.

**Four invariant violations.** `file-handles.ts` and `recovery-journal.ts`
each throw "Database … is blocked by another open connection." and
"IndexedDB transaction aborted"; `save-pipeline.ts` throws two messages about
the saved byte range. All four mean a bug, not a user mistake. An English
string is searchable and pasteable into an issue. They do reach a banner via
`describeError`, and that is accepted.

**`e2e-hooks.ts`'s "No document open".** Test scaffolding; never rendered.

**`APP_TITLE`.** "totoPDF" is a name.

**pdf.js's `pdfjs-page-landmark`.** The component build of pdf.js contains
exactly one localizable string — verified by grepping `pdf_viewer.mjs` for
`data-l10n-id`, which yields one unique id. It is a screen-reader landmark
label on the page container. Reaching it would mean supplying a Fluent `L10n`
implementation to `PDFViewer`, and `pdfjs-dist` ships no `.ftl` files to feed
one. Not worth the machinery for one aria-label.

**DOMException text.** Messages from the file picker and the write-permission
prompt are the browser's, not ours.

## 9. Testing

**New — `test/unit/i18n.test.ts`.** Catalogue conformance:

- `es.json` has exactly `en.json`'s key set — neither missing nor extra.
- Every message declaring placeholders declares the same ones in both files.
- No message is the empty string. An empty translation is always a mistake;
  the one state that renders nothing does so in code, not via the catalogue.
- Every `$N$` referenced in a `message` is declared in that entry's
  `placeholders`.

**New — `t()` unit tests.** Substitution and the no-`chrome` fallback path.

**Changed — `test/unit/manifest.test.ts`.** Assert `default_locale` is `en`,
and that every `__MSG_x__` in the manifest resolves to a key in `en.json`.
The existing three assertions are untouched.

**Changed — `test/e2e/extension-context.ts`.** Pin `--lang=en-US` on the
persistent context. `palette.spec.ts` and `round-trip.spec.ts` both locate
`getByRole('button', { name: 'Highlight' })`, which would fail on a machine
whose Chrome runs in Spanish.

**Not added — a Spanish e2e spec.** Driving Chromium's UI language is
flake-prone, and the catalogue conformance test covers the same ground with
no browser. If a Spanish smoke test is ever wanted, the cheap version is
loading the built `dist/_locales/es/messages.json` and asserting against it,
not launching a second browser.

Everything else — all twenty existing unit specs — must pass unchanged. If a
spec needs editing to accommodate `t()`, that is a signal the fallback path
in §5 is wrong, not the spec.

## 10. Risks

**A missed string.** The inventory in §7 was assembled by grep, and a grep
for capitalized quoted literals cannot see a string built by concatenation.
Mitigation: the plan works file by file against §7's counts, and the final
step re-runs the grep to confirm nothing outside the excluded set remains.

**`default_locale` breaking the unpacked load.** If `_locales/` is not in
`dist/` when the manifest names a `default_locale`, Chrome refuses to load
the extension outright rather than degrading. The build change (§6) and the
manifest change must land in the same commit, and the commit must be verified
by loading `dist/` unpacked, not only by `npm test`.

**Spanish copy longer than English.** Spanish runs roughly 15–25% longer.
`toolbar.ts` lays six buttons plus five swatches plus the zoom and page
controls into one row, already measured at 1280px. "Cuadro de texto" is twice
the width of "Text box". The toolbar needs re-measuring at 1280px in Spanish,
and this is the most likely thing in this design to require a layout change.

## 11. Sequencing

1. `src/i18n/en.json` with all 60 keys, `src/core/i18n.ts`, and its tests.
   Nothing calls `t()` yet.
2. Build plumbing and the manifest, verified by an unpacked load.
3. Call sites, file by file down §7's table.
4. `src/i18n/es.json`, and the conformance test goes green.
5. Toolbar re-measured at 1280px under `--lang=es`. Layout fixed if needed.
